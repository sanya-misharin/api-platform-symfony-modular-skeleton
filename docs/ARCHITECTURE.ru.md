# Модульная архитектура

Проект реализует **модульную архитектуру**, в которой каждая фича/домен изолирована в собственном модуле.

## Что такое модуль?

**Модуль** — это связная единица кода, организованная вокруг конкретного бизнес-домена или фичи. Каждый модуль:

- Живёт в `src/<ModuleName>/`
- Имеет собственную DI-конфигурацию (`di.yaml` или `di.php`)
- Содержит связанные сущности, сервисы, репозитории и API-ресурсы
- Автоматически обнаруживается и загружается фреймворком
- Может быть легко перемещён, переименован или удалён

## Структура модуля

```
src/YourModule/
├── Entity/              # Doctrine entities
├── Repository/          # Doctrine repositories
├── Service/             # Business logic
├── ApiPlatform/         # State processors, extensions
├── Messenger/           # Message handlers (optional)
├── Serializer/          # Custom normalizers (optional)
└── di.yaml              # Dependency injection configuration
```

## Преимущества модулей

### 1. Низкая связанность, высокая связность
- Связанный код лежит вместе
- Чёткие границы модуля
- Минимальные зависимости между модулями

### 2. Масштабируемость
- Команда может работать над разными модулями независимо
- Легко понять область ответственности модуля
- Снижает конфликты при слиянии

### 3. Сопровождаемость
- Легко находить код
- Безопасно рефакторить внутри модуля
- Просто удалять неиспользуемые фичи

### 4. Тестируемость
- Тестирование модулей в изоляции
- Явные зависимости
- Лёгкое мокирование внешних модулей

## Конфигурация автозагрузки

`config/services.php` автоматически импортирует DI-конфигурации из модулей:

```php
$di->import('../src/**/{di}.{php,xml,yaml,yml}');
$di->import('../src/**/{doctrine}.{php,xml,yaml,yml}');
$di->import('../src/**/{api_platform}.{php,xml,yaml,yml}');
```

Это означает:
- Положите `di.yaml` в любой модуль → сервисы регистрируются автоматически
- Добавьте `doctrine.yaml` → загружаются кастомные типы/расширения
- Включите `api_platform.yaml` → применяется конфигурация API

## Пример модуля

Модуль `Example` демонстрирует этот паттерн:

```yaml
# src/Example/di.yaml
services:
    _defaults:
        autowire: true
        autoconfigure: true

    App\Example\:
        resource: '../'
        exclude:
            - '../Entity/'
```

Это автоматически регистрирует все сервисы модуля, кроме сущностей.

## Модуль против бандла

| Аспект | Модуль в `src/` | Symfony Bundle |
|--------|------------------|----------------|
| Назначение | Бизнес-/доменный код | Инфраструктура/интеграция |
| Область | Специфичен для проекта | Универсальный, переиспользуемый |
| Сложность | Простой (только `di.yaml`) | Сложный (классы Bundle + Extension) |
| Использование | Изоляция фич | Расширения фреймворка |

## Лучшие практики

### ✅ Делайте
- Держите модуль сфокусированным на одном домене
- Используйте понятные имена модулей (например, `Invoice`, `Payment`, `User`)
- Выносите общий код в отдельный модуль или `Infrastructure/`
- Документируйте границы и взаимодействия модулей

### ❌ Не делайте
- Не создавайте модули, зависящие от множества других модулей
- Не кладите несвязанные фичи в один модуль
- Не создавайте циклические зависимости между модулями
- Не смешивайте бизнес- и инфраструктурный код в одном модуле

## Межмодульное взаимодействие

Когда модулям нужно взаимодействовать:

1. **События** — развязывайте модули через доменные события
2. **Интерфейсы** — определяйте контракты в общем пространстве имён
3. **Messenger** — асинхронное взаимодействие через шину сообщений
4. **API-вызовы** — для действительно независимых сервисов

## Стратегия миграции

Чтобы преобразовать существующий проект:

1. Определите границы фич
2. Сгруппируйте связанный код по каталогам модулей
3. Создайте `di.yaml` для каждого модуля
4. Уберите глобальную регистрацию сервисов
5. Проверьте изоляцию модулей
6. Итеративно уточняйте границы
